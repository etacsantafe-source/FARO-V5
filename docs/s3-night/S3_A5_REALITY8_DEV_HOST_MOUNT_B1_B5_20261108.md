## B3 — Investigación externa verificable, alternativas y decisión
- SQLite WAL, https://www.sqlite.org/wal.html : un WAL pertenece a UNA base; commit de SQLite no compromete atomicidad del puntero+cinco stores. Además documenta competencia writer/checkpoint y fallos de SQLite históricamente reparados: conservar escritor material global y cerrar lectores antiguos antes del cutover. **ADAPTAR** sus garantías por archivo, no usar WAL como switcher global.
- Android Data Layer, https://developer.android.com/topic/architecture/data-layer : una fuente de verdad por repositorio, lectura offline desde DB canónica y thread-safe; **USAR** la generación activa y los tres owners persistidos, no proyecciones ficticias.
- OWASP Authorization Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html : deny-by-default, least privilege y comprobación en cada solicitud; **USAR** ACL separada y revocable para `MATTER_DUE`, `REMINDER_OCCURRENCE`, `MONTHLY_PLAN_ITEM`.
- Alternativa A (**ADAPTAR/ESCOGIDA**): una extensión puntual del host DEV, reutilizando los dos owners y el graph selector; primera promoción solo tras botón foreground explícito, recuperación exacta al reinicio.
- Alternativa B (**DESCARTAR**): migrar Reality7 **in place** o modificar `RealityStore` para que abra schema8 silenciosamente: rompe descriptor/rollback/no-mutation.
- Alternativa C (**DESCARTAR**): hacer upgrade al pulsar Chat o al iniciar Android: autoriza nueva escritura por una acción de lectura.
- Alternativa D (**DESCARTAR**): un segundo pointer/journal exclusivo de la Activity o una base nueva sin cinco-store graph; genera doble autoridad.
- Sin nueva dependencia, API paga, Sync remota, permiso Android adicional ni cambio en shipping. Versiones de SQLite nativas se verifican solo al gate de compilación; no atribuir vulnerabilidad sin evidencias del empaquetado.

## B5 — Auditoría adversarial previa / criterios de STOP
- Identidad: package exacto `ar.com.faro.alpha.v2coredev`, build debuggable, `V2_ACTIVE_ENABLED=false`. La identidad de host técnico no suplanta login ni concede Apply/Undo; todos los puertos externos siguen ausentes.
- Race: dos Activitys, dos taps, grafo/SQLite anterior aún abiertos, puntero ABA (mismo generationId/sec distinta), lost foreground durante carga, cierre de Session al `onPause`, fail to release global gate. La nueva sesión tiene grant por pointer completo y ACL independiente por dominio; fallar con unavailable, no cero sintético.
- Crash: antes del journal, PREPARING parcial, STAGED antes de VALIDATED, justo después del CAS de pointer, tras `SWITCHED` antes de fence, rollback tras fallo health y `COMPLETED` con fence removido. No auto-adoptar journal ajeno ni hacer limpieza silenciosa.
- Realidad de datos: la versión es limpia pero una instalación DEV puede contener pruebas; no borrarlas ni hacer migración silenciosa. Reality8 es otra generación vacía; Reality7 sigue disponible para rollback de seguridad. Checkpoint físico G15 solo después de terminar B6/B7 y otras dependencias.
- **READY para B6 acotado**: solo si el patch mantiene una fuente de autoridad, quiescence del mismo gate, build dev, test reales y permisos. Si no se consigue demostrar gate compartido o reingreso seguro, detener y mantener el puntero viejo.
