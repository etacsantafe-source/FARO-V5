El host activo V2 sigue deshabilitado por `FaroV5HostCertification.V2_ACTIVE_ENABLED=false`.
2. Android documenta que por defecto los componentes de una app se ejecutan en el mismo proceso, salvo `android:process` de app/componente: https://developer.android.com/guide/components/processes-and-threads. Esto **acota el sistema soportado actual**, no prueba que un lock de proceso valga para un futuro servicio multiproceso. Se agregará guardia del manifest fusionado en CI; si aparece `android:process` el gate falla antes de marcar G1.
3. `FileActiveGenerationPointer.read()` obtiene registro **durable** con secuencia y generación. Los listeners del puntero son solamente del mismo proceso. G1 no depende de listeners para decidir autoridad: `pinnedChatPointer.equals(chatPointer.read())` se revalida en Search y port Chat. La restauración interna de FARO se hace por generación staged + `GenerationSwitchCoordinator.compareAndSet` y journal; ni `WorkspaceBackupSnapshot` ni cinco-store FBS2 guardan el `grant` efímero. El Application no debe restablecer un token anterior tras reinicio.
4. `FaroV5ActiveWorkspaceSearchGrantOwner.kt` es un único propietario revocable por sesión host: `epochOrNull` deniega si readiness/puntero dejó de ser válido; `grantAfterVerifiedHostOpen` emite scope + secuencia de versión + UUID, distinto en cada apertura. B7 `docs/s3-night/S3_A2_G1_HOST_SEARCH_GRANT_B7_PASS_20261104.md` PASS para 6/6 JVM y CI cuatro controles SUCCESS. Nunca equiparar `StateFlow` a autoridad.
5. **Huecos nuevos exactos en `FaroV5CompositionRoot.java`:** `completeStartupRecovery()` y `completeMaintenanceOperation()` llevan readiness a LOCAL_READY pero no readmiten explícitamente el Search grant revocado del grafo todavía abierto. `deliveryGraph()` devuelve un grafo cacheado mientras el **generation ID** coincide; una secuencia distinta tras A→B→A puede hacer que el viejo grafo sobreviva sin reabrirse (sus ports deniegan, pero no se recupera servicio). El owner ya impide resurrección sin autorización, por eso la corrección será readmisión NUEVA, no rehabilitar el token anterior.
6. Ningún resultado físico Android ni prueba real de proceso separado se ha ejecutado. Las suites previas son JVM / package build. El alcance formal de G1 debe decir **single-process host**; una futura app multiproceso/multiusuario exige diseño y certificación nuevos, nunca se considera PASS implícito.

## B5 — AUDITORÍA ADVERSARIAL DE ACEPTACIÓN
- Cada nuevo `epoch` debe ser distinto al de antes de mantenimiento/restauración/reinicio, y un old hit debe ser UNAVAILABLE sin subscriber. No renovar si puntero sequence cambió, recovery pendiente, se cerró el owner o una nueva instancia tiene otro scope. Evento readiness false invalida ANTES de readiness true. Idempotencia: un readiness ready duplicado no cambia ACL activa.
- Tras restore A→B o A→B→A, `deliveryGraph()` no puede reutilizar el graph antiguo sólo por ID; el nuevo abre solo tras validación del pointer y los cinco stores bajo gate. Registro no disponible => deny; no abrir staged ni hacer switch desde G1.
- Entre instancias de puntero con mismo root (sin listener) los stamps deben fallar por relectura durable. **No** reclamar comportamiento multiproceso: el host productivo soportado por este contrato es explícitamente single-process, protegido por guardia del manifest. Otro proceso requerirá gate independiente; no construir uno preventivamente.
- Snapshot de backup nunca contiene grant; reinicio conserva datos pero no autoridad de sesión. `allowBackup=false` limita Android backup automático, el restore propio crea nueva generación; no introducir FBS2/schema/catálogo/egress.
- Fallo de CI, XML inferior, 'manifest no encontrado', cambio extra de ruta, o permiso no READY => STOP/RED_FIX, jamás G1 PASS. CI correcta en SHA final + B7 final separada. **Solo** entonces marcar `S3.A2-G1 CLOSED` dentro del alcance explicitado y dejar G2 OPEN; sigue V2 productiva OFF, S3 0/5 subetapas formales.
