## B3 — Investigación comparada y decisiones
- SQLite https://www.sqlite.org/isolation.html documenta visibilidad de cambios entre conexiones/transacciones, pero **dos read separados no son un snapshot multi-owner**, especialmente si se libera lock entre llamadas; REUTILIZAR SQL/lock del owner, marcar `globalAttentionComplete=false`, no inventar atomicidad entre ambos.
- OWASP Authorization https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html exige deny-by-default y revalidar acceso en cada solicitud. ADAPTAR dos permisos revocables independientes, sin usar Review=ACL.
- OWASP Authorization Patterns https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Patterns_Cheat_Sheet.html separa policy decision y enforcement cerca de recurso: PEP host exige `epochOrNull` y guarda antes/después del read, **sin declarar esto ACL productiva**.
- Android Developers data layer https://developer.android.com/topic/architecture/data-layer y offline first https://developer.android.com/topic/architecture/data-layer/offline-first usan origen local único de verdad; ADAPTAR owner Reality8 y NO snapshot backup como nueva fuente UI.
- Alternativa A USAR: facade de dos read ports tipados a SQL real y binding aislado con ACL externa obligatoria, no habilitado. Alternativa B DESCARTAR: sacar datos del backup FBS2 y entregarlos al UI (autoridad/privacidad/tiempo contaminado). Alternativa C DESCARTAR: crear un nuevo store o replicar estado de due en Home, genera doble truth. Alternativa D DESCARTAR: reutilizar ACL de APPLY u otorgar `true` como policy; confunde autorización de operación y lectura.
- No dependencias/licencias copiadas ni APIs/servicios pagos. Prueba adversarial falsable: cualquier ausencia o cambio de permisos entre owner reads => página nula, sin fuente ni cero sintético.
