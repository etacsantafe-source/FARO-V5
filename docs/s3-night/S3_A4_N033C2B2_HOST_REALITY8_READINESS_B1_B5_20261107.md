## B3 — Investigación externa verificable, límites y pruebas derivadas
1. SQLite WAL: https://www.sqlite.org/wal.html e isolation https://www.sqlite.org/isolation.html. Lectura WAL y checkpoint son independientes del puntero durable; un reopen puede tocar sidecars de SQLite, por eso afirmar **sin mutaciones de dominio**, no «cero bytes escritos». **USAR** preflight activo WAL-aware existente antes de constructor writable; no copiar un archivo db caliente como snapshot sellado. Negativo: schema corrupta o falta de tablas bloquea antes del constructor.
2. Android offline-first oficial (actual): https://developer.android.com/topic/architecture/data-layer/offline-first. El origen local canónico pertenece a data layer; la UI no debe recibir un graph abierto por un booleano temporal. **ADAPTAR** fachada del módulo generation y estado de disponibilidad tipado en próxima unidad de binding, sin otra base ni nube.
3. Aplicación Android real Now in Android: https://github.com/android/nowinandroid/blob/main/docs/ArchitectureLearningJourney.md. Separa data/domain/UI y permite pruebas locales+CI. **REFERENCIA** para devolver un estado/check acotado, sin añadir repositorio ni adoptar flujo de sincronización remota que no aplica. Código/licencia del proyecto externo NO copiado.
4. OWASP API1:2023 https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/. Identidad de generación no demuestra autorización sobre objeto. **USAR** negación por defecto: readiness no confiere capacidad Recordatorio/Plan; exigir ACL revocable y Review humano por objeto en unidad propia. Negativo pendiente: ID legítimo pero ACL revocada debe negar lectura/acción.
5. Room: https://developer.android.com/training/data-storage/room/migrating-db-versions. Las migraciones deben ser explícitas; `fallbackToDestructiveMigration` elimina datos. **DESCARTAR** migración activa silenciosa, fallback o borrar datos por ser instalación V5 limpia; S5 decidirá cleanup.
