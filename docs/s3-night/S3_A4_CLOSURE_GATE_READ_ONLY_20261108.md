## B3 — Evidencia de seguridad/diseño y alternativas
- Android App Sandbox https://source.android.com/docs/security/app-sandbox : UID del proceso es frontera técnica de archivos locales, no autenticación de persona. Admitirlo como principal de instalación SOLO si el producto define explícitamente política monousuario-local y límites de acceso. No inferir esa política del test ni de Profile.displayName.
- OWASP Authorization https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html y BOLA https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ : default DENY y autorización por recurso, no reuse de grant de Search o Apply para Activity/Pendientes.
- SQLite https://www.sqlite.org/isolation.html y Android offline-first https://developer.android.com/topic/architecture/data-layer/offline-first : reutilizar cinco owners oficiales; un contador completo necesita cobertura autoritativa y no puede derivarse de port parcial.
- Alternativa A viable para una siguiente unidad: **política de lectura local monousuario de instalación, explícita y restringida a datos de esa instalación**, basada en Application UID/package verificados, root privativo de FARO, ciclo de vida/recovery y una acción local de acceso, con revocación epoch y puntero completo; nunca exposición de texto sensible sin consentimiento separado. Requiere antes un B1–B5 específico que pruebe todos los límites, incluido funcionamiento en Android y que NO se extrapola a multiusuario. NO declarar esta propuesta una policy ya implementada.
- Alternativa B rechazada: hacer `readPolicy = { "ok" }`, usar UID como login humano, convertir `APPROVED` o puntero/hostReady en grant global, activar `V2_ACTIVE_ENABLED=true` para que el drawer «funcione», o fabricar cero Pendientes a partir de fuentes parciales.
