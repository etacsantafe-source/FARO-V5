## ARCH-03 · DDL destino 9, tablas e integridad exactas para B6
**Todos los objetos siguientes viven en UNA `reality.db` nueva, únicamente STAGED**. Nueva puerta `Finance9Stage` expone user_version9; `RealityStore` normal y Planning8 activo mantienen admisión 7/8. Generación fuente 7/8 inmutable; migración 7→8→9, 8→9; desconocida DENY. Cada DDL e `PRAGMA user_version=9` se ejecutan dentro del MISMO `BEGIN IMMEDIATE … COMMIT` en la copia aislada. `PRAGMA foreign_keys=ON` antes, `foreign_key_check` e `integrity_check` después; interrupción revierte DDL y/o deja sólo stage no activable. Nunca dos SQLite para un mismo Finance Apply.

## B3/B5 · Investigación y prueba local de viabilidad (NO CI de FARO)
Fuentes: `https://www.sqlite.org/lang_transaction.html`, `https://www.sqlite.org/foreignkeys.html`, `https://www.sqlite.org/lang_createtrigger.html`, `https://www.sqlite.org/pragma.html`, `https://developer.android.com/reference/android/database/sqlite/SQLiteOpenHelper`.
Se construyó un **prototipo transitorio Python sqlite3 in-memory** con tablas base simplificadas, DDL representativo 9, CHECK/FK/trigger y transacciones BEGIN IMMEDIATE. Se observaron seis escenarios locales PASS: (1) crear esquema tras marcar fuente7, (2) fuente8, (3) error de segundo efecto de transfer dispara rollback de dos entries, (4) transferencia válida conserva dos entries + vínculo, (5) revoke incrementa epoch e invalida grant, (6) rollback de DDL+user_version restaura estado previo. Ambas pruebas de esquema devolvieron `PRAGMA foreign_key_check=[]`, `integrity_check=ok`, opening heredada LEGACY_UNVERIFIED/NULL.
**Precaución crítica:** prototipo NO es prueba de migración de una Reality7/8 real, no incluye 5 owners, no simula dos procesos, no prueba FBS2, Android, G15 ni fiabilidad de corte físico. Resultado `6/6` vale **sólo** para decisiones SQL acotadas; todo test B6 en repo sigue NOT_RUN.
