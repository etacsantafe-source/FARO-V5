## B3 — alternativas externas evaluadas y decisiones falsables

1. **SQLite transactions** https://www.sqlite.org/lang_transaction.html ; `BEGIN IMMEDIATE` puede fallar con SQLITE_BUSY y COMMIT puede fallar por contención. **Adaptar** una sola transaction `RealityStore.run` con `AtomicApplyTransactionDecision`, rollback en error; sin reintentar ciegamente en el host.
2. **SQLite isolation** https://www.sqlite.org/isolation.html ; WAL y lectura snapshot no reemplazan un fence del owner ni la prueba COMMITTED. **Adaptar** root lease + pointer sequence + commit receipts, no acceso SQL directo del Chat.
3. **SQLite conflict/ABORT** https://www.sqlite.org/lang_conflict.html ; una falla de constraint puede abortar el statement sin cancelar otras operaciones previas. **Adaptar** abortar el AtomicApply completo y usar readback original de E; no declarar éxito por un insert fallido.
4. **Android offline-first** https://developer.android.com/topic/architecture/data-layer/offline-first ; base local como fuente de verdad. **Adaptar** Workspace+Reality locales. **Descartar** sincronización cloud, WorkManager, terceros y pagos para acto Undo DEV.
5. **Alternativa descartada**: integrar host Undo a `S4W05StockConsumptionDevApplyHost` y prestar writer CONSUME, porque el permiso de consumo terminaría habilitando Undo. **Elegida**: host y sesión Undo distintos con flags mutuamente excluyentes.
6. **Alternativa descartada**: workflow fuera de AtomicApply (direct SQLite + `Workspace` best-effort), porque dejaría un físico restaurado sin receipt y riesgo de duplicación tras crash.
7. **Alternativa descartada**: permitir parcial en V1; D/E solo admiten FULL, sin cantidad parcial en canonical `UndoExecutePayload` ni contrato B1–B5.
