## B3 — Alternativas externas y decisión GO/NO-GO
- **GO como arquitectura candidata:** dos authorities independientes, Review humana única y UNO `RealityTransactionScope` SQLite para el cambio de datos, con journal/receipt único. Dos bindings reales futuros deberán ejecutar bajo el mismo `BEGIN IMMEDIATE`. La infraestructura tiene soporte parcial real (W00-A/B).
- **GO solo si la implementación futura demuestra:** policyEpoch/grant/identidad autenticada de CADA owner, con procedencia de confianza, y fencing de revocación serializable a través del mismo COMMIT; por ejemplo política versionada transaccional en la misma Reality con pruebas de dos conexiones/procesos. La solución concreta **NO queda aprobada ni implementada** por este documento.
- **NO-GO actual host dual:** las concesiones locales son efímeras, de un solo owner y protegidas solo en memoria; una revocación externa entre el último check y COMMIT puede escapar. D2 + D1 por sí solos no conceden derechos.
- **NO-GO** dos commits secuenciales, compensación silenciosa, permisos heredados o dos bases ATTACH+WAL como prueba de atomicidad de conjunto. Fuentes oficiales https://www.sqlite.org/lang_transaction.html, https://www.sqlite.org/isolation.html, https://www.sqlite.org/wal.html y https://www.sqlite.org/lang_attach.html. SQLite serializa writes por archivo, pero no serializa una política guardada fuera del mismo dominio de exclusión.
